- 기간: 2026-11-17(화) ~ 11-30(월, 발표). **제출 마감 11-28(토)**(시각은 운영진에 확인 중)
- 팀: 4명(AI Solutions Architect, AI Engineer, Cloud Engineer, Data Scientist)
- 제약: 무료 API와 Azure 크레딧(약 200달러, 11월 말 만료) 범위 안. 크레딧 밖의 유료 옵션은 쓰지 않습니다.
- 기반: **FastAPI 기반**(Python + FastAPI + Postgres(pgvector) + React + Docker + LangGraph, D1 결정). Streamlit 기반은 옮겨 올 강점의 출처로만 씁니다. 결정 사항은 [decisions.md](decisions.md)에 있습니다.

## 1. 목표와 범위

### 1-1. 문제와 원칙
- **문제:** 투자자가 언제든 국내 ETF에 대해 묻고, 근거가 확인된 정확한 답을 규제 범위 안에서 받아야 합니다.
- **설계 원칙**
  - LLM은 숫자와 사실을 만들지 않습니다. 수치는 DB에서만 가져옵니다.
  - 기준일과 투자 고지는 코드가 붙입니다.
  - 검증을 통과한 답만 내보냅니다.
  - 검증 모델은 생성 모델과 다른 모델입니다.

### 1-2. 공통 기능 집합 (이번에 만드는 범위)
- **필수 범위**
  - 제출요건: 배포 URL(README 상단), 하루 질문 상한(D13), README 필수 항목(서비스 개요·팀원별 역할·로컬 실행 방법)
  - 의도: 상품 정보 조회, ETF 비교, 개념·용어 설명(문서 검색), 고위험·추천·범위 밖 요청은 고정 문구. 사실 질문과 섞이면 사실만 답하고 거절 문장을 붙입니다.
  - 에이전트 구조: LLM 계획(수집 도구·인자 결정), 병렬 도구 호출, 재계획 루프 최대 1회(D11 결정됨), 다른 모델의 검증과 재작성 1회

  - 평가: 개발용·시험용 평가, 사용자 테스트 **5명**(11-18 범위 조정)
- **함께 넣는 기능:** 멀티턴(최근 4턴, 직전 ETF 3개, D16 포함), 수준별 답변 3단계(D12 사용자 선택, 기본값 "입문"), 답변 피드백 저장

## 2. 아키텍처

### 2-1. 에이전트 흐름

```
START → preprocess ─(개인정보·인젝션·해킹 차단)────────────────→ template → finalize → END
          │  정규화, ETF 인식(정확 매칭 + 퍼지 후보), 고위험·추천 1차 표시   (LLM 0회)
          └→ orchestrate ── 계획 JSON(의도, 호출할 도구와 인자, 답변 방식, 거절할 부분)
               ∥ 문서 선검색                       ─(전부 고정 문구 유형·되묻기)→ template
               └─ 병렬 호출 → etf_info(DB 조회) / knowledge(문서 검색) / (disclosure, D5)
                              └→ sufficiency(코드, LLM 0회)
                                   ├(부족 & 재계획 0회)→ orchestrate(부족 사유 전달)   ← 재계획 루프(최대 1회)
                                   └→ compose(표 모드: LLM 0회 / 생성 모드: 생성 모델 1회)
                                        ├(생성 실패)→ safe
                                        └→ guard ① 규칙: 근거 없는 숫자·금지 표현·개인정보·고지 누락
                                                 ② 검증 모델(생성 모델과 다른 모델, 위반 문장 인용 요구)
                                             ├ 통과 → finalize(기준일·고지·거절 문장, 코드가 붙임)
                                             ├ 첫 반려 → retry → compose(수집은 다시 안 함)
                                             └ 두 번째 반려·판정 불가 → safe(DB 값 표, LLM 0회)
```

### 2-2. 에이전틱 구조
- **LLM이 계획하고, 도구를 고르고, 결과를 보고 다시 계획합니다.**
  - orchestrate의 LLM이 질문을 읽고 어떤 수집 도구를 어떤 인자로 부를지 계획 JSON으로 정합니다.
  - 도구 결과가 부족하면, 부족 사유를 받은 같은 LLM이 무엇을 더 수집할지 다시 계획합니다.
  - 합성한 답은 다른 LLM이 검증하고, 반려하면 사유를 반영해 다시 씁니다.
- **반복 횟수와 안전 경계는 금융 특성상 코드가 제한합니다.**
  - 재계획은 최대 1회, 재작성은 최대 1회입니다.
  - "부족한가"의 판정, 숫자 대조, 개인정보 차단, 고지·기준일 부착은 LLM이 아니라 코드가 맡습니다.
  - 상한에 닿으면 LLM 생성 없이 DB 값 표나 고정 문구로 끝냅니다.

### 2-3. 재계획 루프 (D11 결정됨: N=1 포함)
- **역할 분담:** 부족한지는 **코드**가 판정하고, 무엇을 더 수집할지는 **LLM**이 정합니다.
- **부족 판정(코드)**
  - 계획한 지표(예: 실부담비용)가 수집 결과에 없음
  - 조건 검색 결과가 0건
  - 문서 검색 최고 점수가 기준보다 낮음
  - 퍼지 후보만 있고 확정된 ETF가 없음
- **부족하면** 부족 사유(빠진 항목, 0건 조건, 낮은 점수)를 붙여 orchestrate로 돌아갑니다. LLM은 이미 모은 결과를 유지한 채 추가 도구와 인자를 계획합니다.
- **상한에 닿으면** 있는 근거로 답하거나, 근거가 없으면 "조건에 맞는 ETF 없음" 또는 "지원하지 않는 상품" 고정 문구로 끝냅니다.
- **비용:** 계획 호출 최대 +2회(JSON 재시도 포함), 토큰 약 +3,000. 생성 호출은 늘지 않습니다.

### 2-5. 모델 배치
- **Azure 안에서 생성과 검증을 서로 다른 모델 계열로 나눕니다.** 예: 생성은 GPT 계열, 검증은 Grok 계열. 같은 모델의 배포 두 개는 같은 모델로 봅니다.
  - Azure에서 쓸 수 있는 채팅 모델 계열: GPT, Grok, Llama, Phi, Mistral, DeepSeek([azure_models.md](azure_models.md)). 외부 무료 API도 쓸 수 있습니다.
  - 다른 제공사 모델은 판매 방식에 따라 크레딧 적용이 갈립니다(같은 문서 2장). 배포 화면에서 Marketplace 단계가 뜨는지 확인합니다.
- **생성:** 크레딧으로 쓸 수 있는 모델 중 가장 성능 좋은 모델(D2). **계획:** 소형 모델.
- **구체적인 모델 선택은 AI Engineer가 Cloud Engineer의 정리([azure_models.md](azure_models.md))를 보고 정합니다**(11-19 Azure 모델 연결 전). 결과는 decisions.md에 기록합니다.
- 할당량 한도 숫자의 단위는 정리에 없어 **확인 필요**입니다. 모델별 단가도 확인 필요입니다(8-1 빈칸).
- **장애 대비(선택):** Azure 뒤에 무료 모델 체인을 둡니다. 폴백이 일어나도 검증 모델은 생성 모델과 달라야 합니다.

## 3. 데이터

- **원칙**
  - 공식 API와 사람이 직접 내려받은 파일만 씁니다. 크롤링하지 않습니다.
  - 모든 값에 출처·수집일·항목별 기준일을 둡니다.
  - 원본 파일은 커밋하지 않습니다.

| 항목 | 출처 | 방식 |
|---|---|---|
| ISIN·단축코드·이름, 종가·NAV·순자산·기초지수 | 공공데이터포털 금융위원회 증권상품시세정보 API(`_V2` 주소) | 자동 수집. ISIN은 API 값만 공식 값 |
| 총보수·상장일·분배 주기·환헤지·레버리지, 실부담비용 | 운용사 상품 페이지·금융투자협회 공시 | 팀이 출처와 함께 직접 기록(수동 CSV, 커밋함) |
| 구성종목 상위 10개 | KRX 정보데이터시스템 화면 CSV | 사람이 내려받음. 파일 이름의 조회일을 기준일로 씀 |
| 투자설명서 본문 | 운용사 페이지 PDF | 사람이 내려받음. 협회 펀드코드로 상품을 확정. 문서 검색 자료 |
| 용어 설명 | 팀이 쓴 짧은 용어집(D6) | 출처·작성일 포함 |

- **검증:** 필수 항목 결측, 음수 보수, 구성 비중 합 100% 초과, ISIN 검증 숫자 오류가 있으면 적재를 멈춥니다. 실부담비용 기준일이 1년 넘게 지났으면 경고합니다.
- **ETF:** 5개입니다. 나스닥100 비교군 3개, 국내 대표 지수 1개, 월배당 1개로 구성합니다(D4).
- **문서 검색:** 투자설명서와 용어집을 청킹해 색인합니다.
  - ETF가 특정되면 그 ETF 문서로 범위를 좁힙니다.
  - 청크 속 숫자도 숫자 대조의 근거로 씁니다.
  - 임베딩은 Azure 임베딩을 설정으로 연결합니다. 벡터 차원은 마이그레이션에 고정(1024)되어 있어, 모델을 바꾸면 차원·재적재를 함께 확인합니다.
  - 질의도 외부 임베딩으로 나가므로 개인정보 차단 뒤에만 호출합니다.
- **적재 위치:** 모든 데이터는 Postgres에 적재합니다. 실데이터 파이프라인(수집 → 검증 → 적재)은 Streamlit 기반에서 옮겨 오고, 스키마를 확장합니다(실부담비용·항목별 기준일·구성종목).

| 1. 규칙 검사(코드) | 근거 없는 숫자(단위 환산·반올림 허용·날짜 대조), 금지 표현(매매 권유·예측 단정·안전·보장·과장, 부정형은 예외), 본문 개인정보, 필수 고지 누락 |
| 2. 검증 모델 | 생성 모델과 다른 모델로 판정합니다. 항목: 근거 일치, 매수·매도 권유, 미래 예측 단정, 근거 없는 순위 표현, 거절해야 할 부분에 답함. 위반 문장 인용을 요구하고, 판정을 받지 못하면 안전 답변으로 보냅니다 |
| 3. 재작성·안전 답변 | 반려되면 1회 재작성하고, 다시 반려되면 DB 값 표로 답합니다(LLM 0회) |
| 4. 고정 문구 | 우선순위는 차단 > 고위험(전망·매매 시점·세금·손실 보상) > 추천 > 범위 밖. 혼합 질문은 사실만 답하고 거절 문장을 붙입니다 |
| 5. 고지·기준일 | 코드가 붙입니다. 상품 정보·비교 답변에만 고지를 붙이고, 항목별 기준일이 ETF마다 다르면 나열합니다 |
| 6. 순위 표현 | 정렬 기준과 기준일을 같은 문장에 씁니다. 총보수만으로 "가장 저렴하다"고 하지 않습니다 |
| 7. 저장·로그 | 대화·피드백은 마스킹해서 저장하고(이미 있음), 로그에는 질문 원문을 남기지 않습니다. 저장 시 마스킹은 외부 호출 전 차단(0단계)을 대신하지 않습니다 |
| 8. 공개 URL | 로그인 없이 사용, 하루 질문 수 상한(D13, DB에 카운트), 넘으면 안내 문구 |

## 5. 평가

- **세트(D17 기준 60문항):** 일반 30, 레드팀 15, 정상 질문 15
  - 시험용 26문항(일반 10, 레드팀 8, 정상 8)은 프롬프트를 고치는 동안 보지 않습니다.

  - 의도 일치와 수치 대조는 자동입니다.
  - 레드팀은 금지 내용 자동 검사 후 사람이 확인합니다.
  - 정상 질문의 과잉 차단은 사람이 확인합니다.
  - 설명형은 2명이 0·1·2점으로 채점합니다.
- **실행 규칙**
  - 한 실행 안에서 생성 모델을 하나로 고정합니다.
  - 캐시를 켜고 돌리고, 응답 시간만 캐시를 끄고 잽니다.
  - 결과의 실제 응답 모델이 다르면 그 문항은 제외합니다.
  - 소규모 세트는 비율과 건수를 함께 씁니다(예: "8문항 중 1건").
- **비용 확인:** 실행 전에 8장 표로 비용을 계산합니다.
- **사용자 테스트:** 배포 URL로 **5명**에게 진행합니다(11-18 범위 조정, 10명 → 5명). ETF 경험 수준(입문·경험·연금·이벤트 반응)을 섞어 모집합니다.

## 6. 용량과 일정

### 6-1. 팀 용량
- 1인 3주(평일 15일) 88~98h에는 공통 시간(스탠드업·통합 빌드·사용자 테스트) 12h가 들어 있습니다. 그래서 1인 하루 모듈 작업은 (88 − 12)~(98 − 12) ÷ 15 = 약 5.07~5.73h입니다.
- 개발 가능일은 **10일**입니다. 평일 8일(11-18~20, 11-23~27)과 주말 2일(11-21·22, D15)입니다. 11-17은 준비일, 11-28은 제출일, 11-29는 발표 준비일, 11-30은 발표일이라 뺐습니다.
- **4명 용량 = 4명 × 10일 × (76~86) ÷ 15 = 약 203~229h**
  - 각자 빠지는 날은 아직 받지 못했습니다(**확인 필요**). 받으면 `빠지는 사람·날 수 × 하루 5.07~5.73h`를 용량에서 빼고 이 식을 고칩니다.
- **공통 기능 집합 공수(FastAPI 기반, 추정): 약 214h** = 232h − 18h(11-18 범위 조정)
  - 범위 조정: 프롬프트 수정 8h → 4h(−4h), 실제 문서 검색 튜닝 8h → 4h(−4h), 사용자 테스트 10명 → 5명(약 −4h), 앱 토큰 집계 대신 Azure 포털 사용량(약 −6h). 재계획 루프와 계획 JSON은 유지합니다.
  - "Azure 채팅 모델이 하나뿐이면 +8h" 조건부 공수는 뺐습니다. Azure에 채팅 모델 계열이 여러 개라 해당하지 않습니다([azure_models.md](azure_models.md)).
  - 온보딩 36h 포함: 코드베이스 익히기 3명 × 약 9h, 도구(Docker·Postgres·React) 익히기 3명 × 약 3h
  - 도구 익히기는 D1 결정 뒤 1인 6h → 3h로 다시 추정했습니다. 팀이 AI로 코딩하므로 설정·코드 초안은 AI가 쓰지만, 띄우기·로그 읽기·고치기는 사람이 해야 해서 절반으로 봤습니다.
- **여유:** 용량 대비 약 −11~+15h(용량 하한 203h면 약 11h 초과, 상한 229h면 약 15h 여유). 계산: 229 − 214 = 15, 203 − 214 = −11. 하한에서는 아직 넘으므로 여유 기능(공시, 추천 비교표, ETF 확장, 로컬 LLM)은 계획에 넣지 않습니다.
- 공수는 추정이므로 11-22(일)에 실제 시간으로 다시 계산합니다.
