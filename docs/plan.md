## 1. 목표와 범위

### 1-1. 문제와 원칙
- **문제:** 투자자가 언제든 국내 ETF에 대해 묻고, 근거가 확인된 정확한 답을 규제 범위 안에서 받아야 합니다.
- **설계 원칙**
  - LLM은 숫자와 사실을 만들지 않습니다. 수치는 DB에서만 가져옵니다.
  - 기준일과 투자 고지는 코드가 붙입니다.
  - 검증을 통과한 답만 내보냅니다.
  - 검증 모델은 생성 모델과 다른 모델입니다.

### 1-2. 공통 기능 집합 (이번에 만드는 범위)
- **필수 범위**
  - 제출요건: 배포 URL(README 상단), 하루 질문 상한(D13), README 필수 항목(서비스 개요·팀원별 역할·로컬 실행 방법)
  - 의도: 상품 정보 조회, ETF 비교, 개념·용어 설명(문서 검색), 고위험·추천·범위 밖 요청은 고정 문구. 사실 질문과 섞이면 사실만 답하고 거절 문장을 붙입니다.
  - 에이전트 구조: LLM 계획(수집 도구·인자 결정), 병렬 도구 호출, 재계획 루프 최대 1회(D11 결정됨), 다른 모델의 검증과 재작성 1회
  - 안전장치: 외부 호출 전 개인정보·인젝션 차단, 규칙 검사(숫자 대조 포함), 코드가 붙이는 고지·기준일

## 2. 아키텍처

### 2-1. 에이전트 흐름

```
START → preprocess ─(개인정보·인젝션·해킹 차단)────────────────→ template → finalize → END
          │  정규화, ETF 인식(정확 매칭 + 퍼지 후보), 고위험·추천 1차 표시   (LLM 0회)
          └→ orchestrate ── 계획 JSON(의도, 호출할 도구와 인자, 답변 방식, 거절할 부분)
               ∥ 문서 선검색                       ─(전부 고정 문구 유형·되묻기)→ template
               └─ 병렬 호출 → etf_info(DB 조회) / knowledge(문서 검색)  ※ 공시(disclosure)는 D5 제외로 끔
                              └→ sufficiency(코드, LLM 0회)
                                   ├(부족 & 재계획 0회)→ orchestrate(부족 사유 전달)   ← 재계획 루프(최대 1회)
                                   └→ compose(표 모드: LLM 0회 / 생성 모드: 생성 모델 1회)
                                        ├(생성 실패)→ safe
                                        └→ guard ① 규칙: 근거 없는 숫자·금지 표현·개인정보·고지 누락
                                                 ② 검증 모델(생성 모델과 다른 모델, 위반 문장 인용 요구)
                                             ├ 통과 → finalize(기준일·고지·거절 문장, 코드가 붙임)
                                             ├ 첫 반려 → retry → compose(수집은 다시 안 함)
                                             └ 두 번째 반려·판정 불가 → safe(DB 값 표, LLM 0회)
```

### 2-2. 에이전틱 구조
- **LLM이 계획하고, 도구를 고르고, 결과를 보고 다시 계획합니다.**
  - orchestrate의 LLM이 질문을 읽고 어떤 수집 도구를 어떤 인자로 부를지 계획 JSON으로 정합니다.
  - 도구 결과가 부족하면, 부족 사유를 받은 같은 LLM이 무엇을 더 수집할지 다시 계획합니다.
  - 합성한 답은 다른 LLM이 검증하고, 반려하면 사유를 반영해 다시 씁니다.
- **반복 횟수와 안전 경계는 금융 특성상 코드가 제한합니다.**
  - 재계획은 최대 1회, 재작성은 최대 1회입니다.
  - "부족한가"의 판정, 숫자 대조, 개인정보 차단, 고지·기준일 부착은 LLM이 아니라 코드가 맡습니다.
  - 상한에 닿으면 LLM 생성 없이 DB 값 표나 고정 문구로 끝냅니다.

### 2-3. 재계획 루프 (D11 결정됨: N=1 포함)
- **역할 분담:** 부족한지는 **코드**가 판정하고, 무엇을 더 수집할지는 **LLM**이 정합니다.
- **부족 판정(코드)** — 11-22 범위 조정 3차로 재계획은 아래 2가지만 합니다.
  - 계획한 지표(예: 실부담비용)가 수집 결과에 없음
  - 조건 검색 결과가 0건
- **재계획 없이 바로 고정 문구:** 문서 검색 최고 점수가 기준보다 낮음, 퍼지 후보만 있고 확정된 ETF가 없음(ETF 이름 애매)
- **부족하면** 부족 사유(빠진 항목, 0건 조건)를 붙여 orchestrate로 돌아갑니다. LLM은 이미 모은 결과를 유지한 채 추가 도구와 인자를 계획합니다.
- **상한에 닿으면** 있는 근거로 답하거나, 근거가 없으면 "조건에 맞는 ETF 없음" 또는 "지원하지 않는 상품" 고정 문구로 끝냅니다.
- **비용:** 계획 호출 최대 +2회(JSON 재시도 포함), 토큰 약 +3,000. 생성 호출은 늘지 않습니다.

### 2-5. 모델 배치
- **Azure 안에서 검증 모델은 생성 모델과 다른 모델로 둡니다(같은 모델의 다른 배포는 같은 모델로 봄). 같은 계열이면 개발용 평가로 검증 효과를 확인합니다.** 결정된 배치(생성 `gpt-6-sol`, 계획·검증 `gpt-6-luna`)와 확인 장치는 [decisions.md](decisions.md) "모델 배치"에 있습니다.
  - Azure에서 쓸 수 있는 채팅 모델 계열: GPT, Grok, Llama, Phi, Mistral, DeepSeek([azure_models.md](azure_models.md)). 외부 무료 API도 쓸 수 있습니다.
  - 다른 제공사 모델은 판매 방식에 따라 크레딧 적용이 갈립니다(같은 문서 2장). 배포 화면에서 Marketplace 단계가 뜨는지 확인합니다.
- **생성:** 크레딧으로 쓸 수 있는 모델 중 가장 성능 좋은 모델(D2). **계획:** 소형 모델.
- **구체적인 모델 선택은 AI Engineer가 Cloud Engineer의 정리([azure_models.md](azure_models.md))를 보고 정합니다**(11-19 Azure 모델 연결 전). 결과는 decisions.md에 기록합니다.
- 할당량 한도 숫자의 단위는 정리에 없어 **확인 필요**입니다. 생성·계획·검증 모델 단가는 8-1에 채웠고, 임베딩 단가는 확인 필요입니다.
- **장애 대비(선택):** Azure 뒤에 무료 모델 체인을 둡니다. 폴백이 일어나도 검증 모델은 생성 모델과 달라야 합니다.

## 3. 데이터

- **원칙**
  - 공식 API와 사람이 직접 내려받은 파일만 씁니다. 크롤링하지 않습니다.
  - 모든 값에 출처·수집일·항목별 기준일을 둡니다.
  - 원본 파일은 커밋하지 않습니다.

| 항목 | 출처 | 방식 |
|---|---|---|
| 단축코드·이름·운용사·기초지수, 순자산(기준일 포함) | 운용사 홈페이지·월간 운용보고서 | 팀이 출처와 함께 직접 기록(수동 CSV, 커밋함) |
| 총보수·상장일·분배 주기·환헤지·레버리지, 실부담비용 | 운용사 상품 페이지·금융투자협회 공시 | 팀이 출처와 함께 직접 기록(수동 CSV, 커밋함) |
| 개념·용어 설명 | 팀이 고쳐 쓴 개념 문서 13개(D6, `data/docs/`) | 출처·작성일 포함. 문서 검색 자료 |

- 공공데이터포털 API 자동 수집(종가·NAV)과 KRX 구성종목은 11-21 범위 조정 2차로 뺐습니다. 평가에 쓰는 값(총보수·실부담비용·상장일·분배주기·기초지수·환헤지·운용사·순자산)만 수동 CSV(`data/real/etf_master.csv`)로 적재합니다. 시세가 없으면 답변 표에서 시세 행을 숨깁니다.

## 4. 안전장치

| 단계 | 내용 |
|---|---|
| 0. 입력 | **모든 외부 API 호출(LLM, 임베딩) 전에** 개인정보·프롬프트 인젝션·해킹 요청을 차단하고 고정 문구로 답합니다. 패턴: 주민·외국인등록번호, 카드, 이메일, 전화, 계좌(종목코드·날짜 오탐 예외). 차단 시 외부 호출 0회를 테스트로 확인합니다 |
| 1. 규칙 검사(코드) | 근거 없는 숫자(단위 환산·반올림 허용·날짜 대조), 금지 표현(매매 권유·예측 단정·안전·보장·과장, 부정형은 예외), 본문 개인정보, 필수 고지 누락 |
| 2. 검증 모델 | 생성 모델과 다른 모델로 판정합니다. 항목: 근거 일치, 매수·매도 권유, 미래 예측 단정, 근거 없는 순위 표현, 거절해야 할 부분에 답함. 위반 문장 인용을 요구하고, 판정을 받지 못하면 안전 답변으로 보냅니다 |
| 3. 재작성·안전 답변 | 반려되면 1회 재작성하고, 다시 반려되면 DB 값 표로 답합니다(LLM 0회) |
| 4. 고정 문구 | 우선순위는 차단 > 고위험(전망·매매 시점·세금·손실 보상) > 추천 > 범위 밖. 혼합 질문은 사실만 답하고 거절 문장을 붙입니다. 계획 JSON `refuse`에 판단 요구 부분과 범위 밖 부분(공시·뉴스 등)을 담습니다(11-21) |
| 5. 고지·기준일 | 코드가 붙입니다. 상품 정보·비교 답변에만 고지를 붙이고, 항목별 기준일이 ETF마다 다르면 나열합니다 |
| 6. 순위 표현 | 정렬 기준과 기준일을 같은 문장에 씁니다. 총보수만으로 "가장 저렴하다"고 하지 않습니다. 순자산처럼 기준일이 상품마다 다르면 상품별 기준일을 함께 씁니다(11-21) |
| 7. 저장·로그 | 대화·피드백은 마스킹해서 저장하고(이미 있음), 로그에는 질문 원문을 남기지 않습니다. 저장 시 마스킹은 외부 호출 전 차단(0단계)을 대신하지 않습니다 |
| 8. 공개 URL | 로그인 없이 사용, 하루 질문 수 상한(D13, DB에 카운트), 넘으면 안내 문구 |
