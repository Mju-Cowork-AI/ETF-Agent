# 협업 규칙

이 문서는 저장소 규칙([dev-guide.md](dev-guide.md), [git-flow.md](git-flow.md))을 기준으로 하고, 팀이 더한 규칙만 적습니다. 다르면 저장소 규칙을 따릅니다.

## 1. 브랜치

- 형식: `타입/짧은-설명`(저장소 규칙). 기본 브랜치는 `dev`입니다.
- 타입: 저장소의 `feat`, `fix`, `refactor`, `docs`, `chore`, `data`, `infra`, `prompt`에 팀이 **`eval`, `test`를 더했습니다.**

| 타입 | 쓰는 때 | 예 |
|---|---|---|
| `feat` | 기능 추가 | `feat/graph-replan-loop` |
| `fix` | 버그 수정 | `fix/guard-date-check` |
| `refactor` | 동작 변화 없는 구조 개선 | `refactor/llm-client` |
| `docs` | 문서 | `docs/readme-run-guide` |
| `chore` | 설정·의존성 | `chore/pin-fastapi` |
| `data` | 데이터 수집·적재·검증 | `data/etf-manual-basics` |
| `infra` | 배포·인프라 | `infra/rehearsal-deploy` |
| `prompt` | 프롬프트 수정 | `prompt/verify-ranking-rule` |
| `eval` | 평가셋·평가 실행기 (팀 추가) | `eval/redteam-set` |
| `test` | 테스트만 추가·수정 (팀 추가) | `test/pii-patterns` |

## 2. 커밋

- 형식: `타입: 내용`(한글 가능, 타입은 브랜치와 같은 목록)
- 예: `feat: 재계획 루프에 부족 사유 전달`, `data: ETF 5개 총보수 출처 추가`
- 한 커밋에는 한 가지 변경만 담습니다. 직접 실행해서 확인한 뒤 커밋합니다.

## 3. PR과 병합

- 모든 작업은 브랜치 → **`dev`로 PR**. `dev`·`main`에는 직접 push할 수 없습니다.
- **기본:** CI(`ci`: ruff, compileall, pytest)가 통과하면 **작성자가 직접 squash 머지**합니다(저장소 규칙).
- **승인 필수(팀 추가):** 아래를 고치는 PR은 팀원 **1명 승인** 후 머지합니다.
  - 개인정보 차단(외부 API 호출 전)
  - 가드(규칙 검사·검증 모델)
  - 숫자 대조
  - 데이터 파이프라인(수집·검증·적재)
- **옮겨 온 코드:** 다른 코드베이스에서 옮겨 온 코드는 **원 코드 작성자가 리뷰**합니다.
- **릴리스:** `dev` → `main`은 릴리스 권한자 1명만 merge commit으로 머지합니다.
- PR 제목은 `타입: 내용`. 본문에는 관련 작업 카드 번호, 바꾼 것, 확인 방법(명령), 남은 문제를 적습니다.
- 11-25(수) MVP 이후에는 새 기능 PR을 받지 않습니다(버그·문서·평가만).

## 4. 작업 카드

- **작업 카드(GitHub Issue) 1개 = 담당자 1명 = 브랜치 1개**
- 카드에는 완료 기준을 한 줄 이상 적습니다.
- 막히면 카드에 댓글로 남기고 스탠드업에서 말합니다.

## 5. 키와 비밀값

- 키의 원본은 **Azure Key Vault**에 두고, CI·배포용은 **GitHub Secrets**에 복사합니다(저장소 규칙, `scripts/set-secret.sh`). 로컬은 `.env`에만 둡니다.
- 이름 규칙: Key Vault는 하이픈(`LLM-API-KEY`), GitHub Secrets와 `.env`는 언더스코어(`LLM_API_KEY`).
- **채팅·커밋·로그·스크린샷에 키를 넣지 않습니다.** 실수로 올라가면 즉시 폐기·재발급하고 팀에 알립니다.
- **Azure 키 관리자를 1명 지정합니다**(채팅방 결정, [decision_board.md](decision_board.md)). 관리자가 Key Vault 등록과 팀원 `.env` 전달 방식을 맡습니다.
- Gemini·Groq 같은 무료 키는 팀원 각자 자기 것을 씁니다. 여러 키를 번갈아 쓰는 코드는 만들지 않습니다(한도 우회 소지).
- `.env.example`에는 이름과 설명만 두고 값은 넣지 않습니다.

## 6. 커밋 금지 파일

| 대상 | 이유 |
|---|---|
| `.env`, `.env.local` 등 비밀값 파일 | 키 유출 |
| 외부 원본 데이터(KRX 구성종목 CSV, 투자설명서 PDF 등) | 재배포 금지 |
| API 응답 원본 | 각자 자기 키로 생성 |
| DB 파일(SQLite 파일, DB 덤프), 벡터 색인 | 원본으로 각자 생성 |
| LLM 응답 캐시, 사용량 기록 | 개인별 |
| 평가 결과 원본 | 개인별(요약 표만 문서로 커밋) |
| 개인 IDE·Claude Code 로컬 설정 | 개인별 |
| 사용자 테스트 원문(질문·답변 로그) | 질문 원문이 남음 |

- 팀이 공개 자료를 보고 직접 적은 수동 값(총보수 등)과 출처는 원본이 아니므로 커밋합니다.
- 커밋 전에 `git status`로 위 파일이 없는지 확인합니다. 위 항목은 `.gitignore`에 들어 있습니다.

## 7. 테스트

- `pytest`는 **mock으로만** 돌립니다. 실제 LLM·임베딩·외부 데이터 API를 부르지 않습니다(크레딧과 무료 한도 보호).
- 실제 모델 확인은 손 테스트나 평가 실행기로만 하고, 실행 전에 비용을 계산합니다.

## 8. 크레딧과 사용량

- **예산 알림:** Azure 구독에 단계별 예산 알림을 켭니다(Cloud Engineer).
- **하루 질문 상한:** 공개 URL에는 하루 질문 수 상한을 두고, 넘으면 안내 문구를 보여 줍니다. 상한 값은 비용 계산으로 정합니다.
- **평가 전 비용 확인:** 평가를 돌리기 전에 질문당 토큰 × 문항 수로 비용을 계산하고 남은 크레딧과 비교합니다.
- 남은 크레딧과 모델별 토큰은 스탠드업에서 공유합니다.

## 9. 데이터

- **크롤링 금지.** 공식 API(공공데이터포털, OpenDART)와 사람이 직접 내려받은 파일만 씁니다.
- 모든 값에 출처와 수집일, 항목별 기준일을 남깁니다.
- 실제 데이터가 없으면 누가 봐도 가짜인 샘플만 쓰고, 파일명에 `SAMPLE`을 넣습니다.

## 10. 개인정보

- **개인정보(주민·외국인등록번호, 카드, 계좌, 전화, 이메일)는 모든 외부 API 호출(LLM, 임베딩) 전에 차단합니다.**
- 차단된 질문은 외부 호출이 0회인지 테스트로 확인합니다.
- 저장하는 대화·피드백은 마스킹하고, 로그에는 질문 원문을 남기지 않습니다.

## 11. 도구 규약

- 린트·포맷은 **ruff**, 검사는 **`make check`**(CI와 같음: ruff → compileall → pytest)입니다(저장소 규칙). PR 전에 실행합니다.
- 웹 화면(TypeScript)의 린트와 Python 버전은 코드 들여오기 방식이 정해진 뒤 맞춥니다(채팅방 결정, 11-18 18:00).
